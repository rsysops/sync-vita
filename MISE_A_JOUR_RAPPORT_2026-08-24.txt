===============================================================================
OBJECTIF DE L'APPLICATION
===============================================================================
Créer une application Windows unique (`VitaSync.exe`) permettant de jouer
à des jeux PS Vita entièrement depuis le PC, via un câble USB, sans WiFi.
L'application doit combiner dans une seule fenêtre :
- Affichage vidéo en temps réel de l'écran de la Vita (la Vita se comporte
  comme une webcam USB standard — protocole UVC/USB Video Class).
- Contrôle complet de la console : les touches du clavier et les mouvements/
  clics de la souris du PC doivent être transmis à la Vita et interprétés
  comme des appuis sur les boutons physiques et mouvements des joysticks
  analogiques.
- Émulation de l'écran tactile : clic souris sur l'image = pression tactile
  à l'endroit exact sur la Vita.
- Mode FPS : capture de la souris pour contrôler la caméra des jeux à la
  première personne sans limitation par les bords de l'écran.

PHASE 9 — Résolution du bug de contrôle (les boutons ne marchaient pas)
-----------------------------------------------------------------------
Le mystère de la phase 8 est résolu. Il y avait QUATRE problèmes empilés :

9.1  DÉSACCORD DE TAILLE DE RAPPORT HID (bloquant total).
     Descripteur déclarait 16 octets de données + Report ID = 17 octets
     câble. L'app envoyait 16 octets, la Vita recevait dans 16 octets.
     Windows exige WriteFile == OutputReportByteLength EXACT.
     → CORRECTION : alignement strict des 3 couches (descripteur /
     tableau C# / buffer kernel). Le rapport fait maintenant 64 octets
     total (1 Report ID + 63 data bytes).

9.2  CACHE CPU PÉRIMÉ.
     Après écriture DMA USB, le CPU relisait ses lignes de cache au lieu
     de la RAM fraîche → il appliquait en boucle des zéros au lieu des
     vraies valeurs. Symptôme : btns=000 sticks=0/0/0/0 malgré transport OK.
     → CORRECTION : ksceKernelDcacheInvalidateRange(pc_hid_report, sizeof)
     AVANT chaque lecture post-DMA.

9.3  PAS DE RÉARMEMENT EN CAS D'ERREUR.
     pc_hid_recv_on_complete retournait sans réarmer si returnCode<0,
     tuant définitivement le canal après le premier accroc.
     → CORRECTION : réarmement systématique même en cas d'erreur.

9.4  BITS GÂCHETTES FILTRÉS PAR LE FIRMWARE.
     Les bits L/R classiques (0x0100/0x0200) passent le transport mais
     sont IGNORÉS par la fusion d'émulation du système (confirmé par
     PHYS btns montrant l'injection sans effet en jeu).
     → CONTOURNEMENT VALIDÉ : injecter aussi les alias matériels
     L1/R1 (0x0400/0x0800) en plus des bits classiques.
     Résultat : les gâchettes fonctionnent !

9.5  SLOTS D'ÉMULATION SÉPARÉS.
     L'analogique (slot 0) écrasait la partie boutons du même slot.
     → Solution : analogique slot 0, boutons slots 1-3 combinés.

9.6  DÉRIVE DU STICK corrigée.
     Chaque console a un point de repos propre (~124 au lieu de 128).
     Au branchement, le plugin mesure la position de repos réelle via
     ksceCtrlPeekBufferPositive et exprime toutes les valeurs RELATIVEMENT
     à ce neutre. Plus aucune dérive.

Pièges découverts et corrigés (À NE JAMAIS REFAIRE) :
11.1  Ne JAMAIS mettre tout le tampon SceTouchData à zéro. Conserver
      timeStamp et status de chaque tampon : si le timestamp est figé,
      le jeu considère « pas de nouvelle donnée » et ignore le toucher.
11.2  Identifiant de doigt : incrémenter l'id à CHAQUE nouveau contact
      (les jeux associent appui->relâchement par id ; id réutilisé =

11.3  ESPACE DE COORDONNÉES : mesuré empiriquement avec un vrai doigt

      960×544 a été explorée puis abandonnée.
11.4  *** RÈGLE D'OR *** Quand le PC n'appuie pas, NE RIEN ÉCRIRE dans

      permanente EFFACE le vrai doigt physique. Symptôme : « tactile
      mort avec le plugin, vivant sans (boot avec L maintenu) ».
11.5  Port audio inconnu (params non enregistrés) : NE RIEN FAIRE.
      Lire un port avec des params par défaut trop larges cause un
      overread mémoire → panic noyau → redémarrage silencieux.
      Symptôme : « introuvable » juste après connexion car le premier
      bip système déclenchait la lecture avec ch=2 défaut alors que le
      buffer était mono.
11.6  GESTES EN JEU (Killzone) : la réécriture complète de l'historique
      avec la position courante détruit la trajectoire. Un système de
      piste (trail) a rendu les gestes fonctionnels mais s'est révélé
      fragile. Limitation connue : sous-menus profonds KZ inactifs.
11.7  La position du curseur doit être gérée via RAW INPUT (WM_INPUT),

      SetCursorPos génère des événements parasites inversés.

PHASE 14b — SON VIA VIDÉO NV12 (tentative, puis désactivé)
----------------------------------------------------------
Approche : embarquer du PCM 24kHz mono s16 dans les 8 dernières lignes Y
du flux vidéo NV12 via un encodage 2 bits/pixel (niveaux {25,95,165,235}).
Le PC extrait les données depuis les lignes BGRA8 en bas de l'image,
vérifie le CRC, et alimente waveOut 24kHz mono s16.

RESULTAT : audio reconnaissable mais craquements inhérents non résolus.
DÉSACTIVÉ en build 89 (tous les flags audio à 0). Code conservé in situ.

### Format d'encodage
- Payload : PCM mono 24kHz s16 LE, max 1728 octets/frame
- En-tête AV : 'A','V',seq,len_lo,len_hi,crc (6 octets)
- Balise TSEL : 'T','S','E','L' + len_lo, len_hi, crc (7 octets)
- Encodage : 1 octet = 4 pixels BGRA. 2 bits par canal, niveaux {25,95,165,235}
- Capacité max : 8 rows × 960 pixels ÷ 4 = 1920 octets/frame
- Débit nécessaire : 48000 octets/s (24kHz × 2 bytes)
- Débit réel mesuré : ~1024 octets/frame × 30fps ≈ 30720 octets/s

### Flags de compilation (vita-udcd-uvc/src/main.c, lignes 162-170)
  ENABLE_AUDIO_CAPTURE  = 1  (hooks audio + déclarations, gardé même désactivé)
  ENABLE_AUDIO_PUSH     = 0  (hook sceAudioOutOutput : DÉSACTIVÉ)
  ENABLE_AUDIO_HOOKTRY  = 0  (tentative installation hooks : DÉSACTIVÉ)
  ENABLE_AUDIO_RECORDERS= 0  (hooks OpenPort/SetConfig : DÉSACTIVÉ)
  ENABLE_AUDIO_INJECT   = 0  (encodage PCM dans rows Y : DÉSACTIVÉ)
  ENABLE_AUDIO_STREAM   = 0  (audio via EP2 HID IN : déjà désactivé)
  ENABLE_AUDIO_MUTE     = 0  (mute haut-parleur Vita)
  ENABLE_AUDIO_PIDGRAB  = 0  (capture PID audio)
  ENABLE_AUDIO_BISECT_PASSTHRU = 0

  Pour réactiver : remettre à 1 CAPTURE, PUSH, HOOKTRY, RECORDERS, INJECT
  (et optionnellement MUTE). Puis make clean && make côté Vita.

### PC — réactivation audio (windows/MainForm.cs, ligne ~637)
  if (buf[0] == 1 && buf[1] != 0xC7) {
      continue;  // SUPPRIMER pour réactiver l'audio HID

### Erreurs corrigées pendant le développement
1.  Crash pBuffer (builds 65-66) : déréférencement direct de pBuffer
    dans le hook → data abort. Fix : ksceKernelCopyFromUserProc avec
    SceUID COMPLET (pas &0xFF).
2.  Crash dcache (builds 65-66) : ksceKernelDcacheCleanInvalidateRange
    trop gros. Fix : ksceKernelDcacheCleanRange sur 8 rows uniquement.
3.  PID tronqué (build 78) : &0xFF n'est pas un handle valide.
    Fix : SceUID complet de ksceKernelGetProcessId().
4.  Bug k-loop (build 88) : boucle for(k=0;k<4) écrasait sym[0..3] à
    chaque itération → 75% des données audio perdues. Fix : 1 byte par
    groupe de 4 pixels.
5.  uvc_frame_term crash : appelé au timeout du worker pendant DMA USB.
    Fix : supprimé du chemin timeout.
6.  Buffer circulaire 16/4 slots (builds 89v1, 90) : BSS trop gros →
    Vita ne charge pas le plugin. Diagnostic non terminé.
7.  Double-count HID+video (build 89 PC) : audio arrivait par 2 chemins
    simultanément → queue gonfle → délài 2-3 secondes. Fix : désactiver
    le chemin HID.
8.  WaveOut gaps : Thread.Sleep entre writes → underrun → craquements.
    Fix partiel : 4 buffers × 4800 bytes, seuil minimum 600 bytes.
9.  List<byte> GC pauses : GetRange/RemoveRange O(n) + allocations →
    micro-stutters. Fix : ring buffer natif byte[96000] head/tail.
10. Doublons audio (build 91) : 2 slots lus sans tracker séquence →
    données d'une frame précédente relues → clicks. Tentative de fix
    avec aud_stage_read_seq : compile mais craquements restent.

### Problème fondamental non résolu
Le hook produit ~1024 octets par appel. Avec double-buffer (2 slots),
on obtient ~1024-2048 octets/frame. À 30fps = 30720-61440 octets/s.
Le minimum est 48000. Quand le jeu appelle sceAudioOutOutput une fois
par frame → 30720 octets/s = 64% du nécessaire → 37% des samples
manquants → craquements inhérents à l'approche.

### Pistes pour résoudre (non implémentées)
1. Plus de lignes : AUD_ROWS de 8 à 12+ (plus de capacité, bande plus
   visible en bas de l'écran)
2. Plus de slots : 4+ avec drain correct (nécessite diagnostiquer le
   crash BSS du ring buffer)
3. Canal séparé : EP2 HID en parallèle de la vidéo
4. Échantillonnage 48kHz : double le débit mais nécessite plus de pixels
5. Interpolation PC : remplacer samples manquants par interpolation
   linéaire entre samples adjacents

### Taille du plugin
- Avec audio : ~16160 bytes
- Sans audio (actuel, tous flags à 0) : 13907 bytes
